# Kit-less Isaac Lab and staged curricula

*2026-10-02*

A note on sourcing: today only GitHub pages could be opened, so every item below links to a repository or release page that was actually read. Some of the underlying papers are older than a week; what is new is the code or release, and dates are given.

## Robot learning

### [Isaac Lab v3.0.0-EA](https://github.com/isaac-sim/IsaacLab/releases)
NVIDIA Isaac Lab team, early-access release from 16 September.

Isaac Lab 3.0 can now run robot learning without installing Isaac Sim at all ("kit-less"), and its physics layer is split into swappable backends: PhysX, Newton and OVPhysX. Data stays on the GPU through Warp-native, zero-copy pipelines, there is a single `isaaclab` CLI for training and playback, and visualization can go through lightweight viewers like Viser or Rerun instead of the full Omniverse app. The release notes include guidance on moving locomotion policies between PhysX and Newton, and the earlier 3.0 beta added rough-terrain locomotion presets for bipeds. For a club training a custom humanoid this matters twice: a lighter install is easier to run on a shared cluster, and training on one physics engine while checking on another is a cheap sim-to-sim test before touching hardware. Caveat: this is an early-access build, so expect API churn, and a policy that transfers PhysX-to-Newton is still not proof it transfers to your motors.

### [RoboNaldo: humanoid soccer shooting](https://github.com/OpenDriveLab/RoboNaldo)
OpenDriveLab; CoRL 2026 oral, code released earlier and trending on GitHub this week.

RoboNaldo trains a Unitree G1 to kick a ball accurately and hard using a three-stage curriculum in Isaac Lab with PPO (RSL-RL). Stage 1 learns to track a reference kicking motion on flat ground, stage 2 adapts that to shooting a static ball over a widening range of targets, and stage 3 handles an incoming moving ball with adaptive sampling of hard cases. The same policy is exported to ONNX and run on the real robot, with a separate deploy repository. Why it matters: it is a complete, readable example of the recipe most humanoid skill papers now follow, motion-tracking reward first, task reward layered on top, curriculum to widen the task. Caveat: the release covers right-foot kicks from one reference clip on a commercial robot, so for a custom humanoid the retargeting and actuator modelling are left to you.

### [EasyWAM](https://github.com/OpenMOSS/EasyWAM)
OpenMOSS team; first release 2 September, latest update 29 September.

EasyWAM is a single codebase for training and evaluating "world action models": policies built on video diffusion transformers that predict future frames and actions together, rather than mapping images straight to actions as a standard VLA does. It implements five variants, from a single shared video/action DiT to dual-backbone mixtures and an inverse-dynamics version, on top of video backbones such as Wan2.2-TI2V-5B and Cosmos-Predict2.5-2B, with full fine-tuning or LoRA. The most recent update adds official LIBERO-Pro evaluation and a standardized data pipeline, alongside RoboTwin, RoboDojo and RoboCasa365 support. It reports LIBERO averages of roughly 97-99% with full training and claims 2.68x throughput over the FastWAM code it grew from. Caveat: these are all tabletop manipulation benchmarks in simulation, LIBERO is close to saturated, and nothing here touches legged robots yet; it is the thing to read for "phase two" (tasks), not walking.

## Learn

**What the walking policy actually outputs: PD targets and action spaces**

Almost every sim-to-real humanoid walking policy has the same shape. The network runs at a low rate, typically 50 Hz, and outputs one number per joint. That number is not a torque. It is an offset added to a default standing pose, giving a target joint position q_target = q_default + action_scale * a.

A PD controller running much faster on the motor driver (often 500 Hz to a few kHz) turns that target into torque: tau = Kp * (q_target - q) - Kd * q_dot. So the policy decides where joints should go, and the PD loop decides how stiffly they get there.

Why not output torques directly? Torque policies have to learn stabilisation from scratch at 50 Hz, which is too slow to react to contacts, and they are very sensitive to motor and friction errors. Position targets give a built-in spring-damper around a sensible pose, which makes exploration safer and the sim-to-real gap smaller.

The choices that matter in practice:

- **Kp and Kd.** High gains make the robot stiff and precise in sim but jittery and impact-sensitive on hardware; low gains look compliant but lag. A common start is gains per joint group (hips and knees stiffer, ankles and arms softer) and a Kd of about a tenth to a twentieth of Kp. Whatever you choose, sim and hardware must use exactly the same values.
- **Action scale.** Typically 0.25-0.5. Too large and early random actions slam joints into limits; too small and the policy cannot reach a full stride.
- **Default pose.** Slightly bent knees give the controller room to work in both directions.
- **Clipping and torque limits.** Clip actions and model the motor's torque-speed limit in sim, otherwise the policy learns moves the real actuators cannot produce.

## Seeds

- [OmniSim](https://github.com/omnilink-tech/omnisim): a robotics simulator on the Newton physics engine whose main user is a coding agent, with about 38 HTTP/JSON endpoints mirrored as MCP tools so an agent can query contacts, joint limits and sensor states while it debugs or writes controllers. Idea worth stealing: design robotics tooling for agents first, humans second.
- [Inspect Robots](https://github.com/robocurve/inspect-robots): an alpha, MIT-licensed eval harness that runs any policy (LLM or VLA) on any embodiment, real arms and humanoids or Isaac Lab, with tasks written as Python scenes plus scorers and logs viewable in Rerun. Idea worth stealing: whoever owns the trusted benchmark for physical AI gets a lot of leverage over the field.
- [wb_humanoid_mpc](https://github.com/manumerous/wb_humanoid_mpc): an open BSD-licensed whole-body nonlinear MPC for humanoids, running in real time on a Unitree G1, with 1X support credited and 1X Neo listed as coming. Idea worth stealing: a model-based controller is a strong baseline and a source of reference motions for an RL policy, and having one for your own robot makes RL debugging much easier.
